# Правила оформления Pull Request

Документ описывает правила работы с Pull Request (далее PR) внутри команды. Правила дополняют `git.md`.

## PR-01. Размер PR

* Целевой объем изменений — **до 400 строк**. После этой границы качество ревью будет снижаться и время для проведения ревью будет расти.
* Ориентиры:
  * 1–100 строк — быстрое и точное ревью;
  * 100–300 строк — приемлемое ревью;
  * 300–500 строк — качество падает;
  * больше 500 строк — задержка ревью и повышенный риск багов после слияния.
* Если задача крупная, она разбивается на серию stacked PR, каждый из которых нацелен на ветку предыдущего.
* Рефакторинг и добавление новой функциональности оформляются разными PR.

## PR-02. Заголовок и описание

* **Заголовок** — одна строка, отражающая суть и причину изменения. Заголовок начинается с идентификатора задачи в формате, описанном в `git.md`.
* **Описание** обязано отвечать на три вопроса:
  1. Что изменено? — краткое резюме на 2–3 предложения.
  2. Зачем? — расширение функционала, баг, рефакторинг.
  3. Как ревьюить? — точка входа, на что обратить внимание, что и как протестировать.
* В описании указываются:
  * ссылка на задачу в трекере;
  * причина изменения;
  * скриншоты или видео для UI-изменений;
  * заметки о деплое.
* Запрещено:
  * вставлять историю коммитов вместо описания;
  * писать «см. задачу» без раскрытия контекста.

## PR-03. Подготовка PR автором

* Перед открытием PR автор:
  * прогоняет сборку через CMake пресеты согласно `build.md`;
  * прогоняет `clang-format` и `clang-tidy`;
  * запускает все имеющиеся тесты локально.
* PR открывается из ветки с префиксом, описанным в `git.md`.
* PR из всех веток направляется в `develop`.


## PR-04. Тесты

* В идеале новый код сопровождается тестами.
* Тесты покрывают как успешный сценарий, так и сценарии ошибок.
* Все существующие проверки должны быть зелеными в CI до ревью.
* Для UI и пользовательских сценариев в описание добавляется раздел с шагами ручной проверки.

## PR-05. Процесс ревью

### 5.1. Действия ревьюера до начала чтения кода

* Прочитать описание; при недостатке информации запросить уточнение, не открывая изменения.
* Оценить размер; если PR превышает 400 строк изменений, запросить разбиение.
* Дождаться зеленого CI.

В случае несоответствия правилам в комментарии будут указаны параграфы из этого документа и реквест будет закрыт.

### 5.2. Формат комментариев

Каждый комментарий может начинаться с одного из префиксов:

* `blocking:` — обязательная правка до слияния;
* `question:` — запрос информации;
* `suggestion:` — предложение, которое автор может принять или отклонить;
* `nit:` — мелкое замечание, не блокирует слияние.

Approve без проверки запрещен. В approve кратко указывается, что было проверено.

### 5.3. Закрытие комментариев ревью

* Автор PR **не закрывает** комментарии ревьюера сам, даже если правка внесена.
* После того как автор учёл замечание, он ставит на исходный комментарий реакцию (например, ✅ или 👍) и при необходимости отвечает коротким сообщением со ссылкой на коммит с правкой.
* Закрывает (resolve) комментарий **только ревьюер**, который его оставил, после того как убедился, что замечание действительно учтено.
* Исключение: комментарии с префиксом `nit:` автор может закрывать сам, если правка очевидна и не требует повторной проверки.

## PR-06. Разделение крупной задачи на серию PR

Если задача в трекере не укладывается в лимит из PR-01, она реализуется серией stacked PR. Каждая ветка отходит от предыдущей, а не от `develop`. Это сохраняет цепочку зависимостей и делает каждый PR самостоятельно ревьюируемым.

### Принципы разбиения

* Один PR — один логический шаг. Шаг должен компилироваться и проходить тесты.
* Шаги должны быть модульными и не содержать изменения разных частей продукта.
* Изменения публичных API вносятся в первом PR серии, чтобы остальные PR могли на них опираться.
* Тесты добавляются в том же PR, что и код, который они покрывают.

### Пример: задача `VERIFY-200` — добавить верификацию стримингового RDMA GPU сервиса 

Допустим, задача требует около 1000 строк изменений: новые верификационные сервисы, сэмплы, изменения внутри фреймворка, интеграционные тесты с конфигами. Один PR такого размера ревьюить нельзя. Серия выглядит так:

```
develop
   └── feature/verification-gpu-services                      (PR #1, ~300 строк)
        └── feature/verification-gpu-samples                  (PR #2, ~400 строк, ветка от feature/verification-gpu-services)
             └── feature/fix-gpu-server-blocking              (PR #3, ~100 строк, ветка от feature/verification-gpu-samples)
                  └── feature/verification-gpu-configs        (PR #4, ~100 строк, ветка от feature/fix-gpu-server-blocking)
```

### Правила работы с серией

* В заголовке каждого PR указывается порядковый номер: `[VERIFY-200] (2/4) Verification GPU samples`.
* В описании каждого PR обязательно:
  * ссылка на родительский PR;
  * ссылка на корневую задачу;
  * краткое описание места этого шага в цепочке.
* PR сливаются строго по порядку. После слияния PR `N` ветка PR `N+1` перебазируется на `develop`.
* Если ревью PR `N` приводит к правкам публичных API, эти правки протаскиваются по всей цепочке автором до повторного ревью.
* Закрывать корневую задачу в трекере следует только после слияния последнего PR серии.

## PR-07. Антипаттерны

Следующие практики недопустимы:

* PR на несколько тысяч строк, объединяющий несвязанные изменения;
* approve в течение пары минут без следов проверки;
* ревью, состоящее только из стилистических замечаний при игнорировании логики;
* PR, висящие неделями без активности и многократно перебазированные;
* смешивание рефакторинга с новой функциональностью в одном PR;
* объединение исправления бага с не относящимися к нему улучшениями.
