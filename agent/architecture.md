# Архитектура приложений

Документ задает обязательные архитектурные правила для всех новых модулей и сервисов. Существующий код приводится к этим правилам по мере доработки.

## ARC-01. Допустимые архитектурные подходы

| Подход | Когда применять |
| --- | --- |
| Layer architecture | По умолчанию для большинства сервисов. |
| Hexagonal architecture | Сервисы с несколькими доменами и несколькими вариантами транспорта, хранения или интерфейса. |
| MVC | Несложные GUI-приложения, чья задача — предоставить интерфейс к данным. |

## ARC-02. Layer architecture

### 2.1. Слои

Сверху вниз:

1. **Transport / UI** — HTTP, gRPC, CLI, GUI. Принимает внешние запросы и переводит их в вызовы сервисов.
2. **Service** — прикладная логика. Координирует работу моделей и репозиториев, реализует сценарии использования.
3. **Domain (models)** — доменные сущности и их инварианты. Не зависят ни от каких других слоёв.
4. **Storage / infrastructure** — репозитории, клиенты внешних систем, файловая система, БД.

### 2.2. Правила зависимостей

* Зависимости направлены строго сверху вниз: верхний слой знает о нижнем, нижний о верхнем — нет.
* Слой Domain не зависит ни от чего из проекта, кроме стандартной библиотеки и допустимых сторонних библиотек без бизнес-логики.
* Слой Storage реализует интерфейсы, объявленные в Service или Domain. Сервисы работают с интерфейсами, а не с конкретными реализациями.
* Циклические зависимости между модулями и слоями запрещены.

### 2.3. Порядок проектирования

1. Если приложение хранит данные — сначала проектируется схема хранения.
2. Затем — доменные модели поверх этой схемы.
3. Затем — сервисы.
4. В последнюю очередь — транспортный слой и интерфейс пользователя.

## ARC-03. Hexagonal architecture

* Ядро (domain + services) изолировано от внешнего мира портами (interfaces).
* Адаптеры реализуют порты для конкретного транспорта, хранилища или внешнего сервиса.
* Ядро не знает о существовании адаптеров.
* Любая внешняя зависимость подключается через порт. Прямой импорт SDK внешних систем в ядро запрещён.
* Тесты ядра запускаются без поднятия адаптеров; адаптеры покрываются отдельными интеграционными тестами.

## ARC-04. MVC

* Применяется только в GUI-приложениях.
* Model хранит состояние и инварианты, не знает о View и Controller.
* View не содержит бизнес-логики, только отображение и пользовательский ввод.
* Controller связывает Model и View, обрабатывает события и вызывает прикладную логику.
* Обращения View напрямую к Model в обход Controller запрещены.
