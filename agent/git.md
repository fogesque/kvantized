# Правила для системы контроля версий

Документ задает обязательные правила работы с Git. Дополняет `pullrequest.md` и `build.md`.

## GIT-01. Структура веток

* `main` — только production-ready код, прошедший все проверки и ревью. История линейная.
* `develop` — основная ветка разработки. В неё сливаются все feature-, hotfix-, test-, experimental-PR.
* Слияние в `main` выполняется только из `develop` и только релизным PR.

## GIT-02. Префиксы веток

Каждая ветка обязана начинаться с одного из префиксов:

| Префикс | Назначение |
| --- | --- |
| `feature/` | Новый функционал. |
| `hotfix/` | Срочное исправление, требующее быстрого попадания в `develop`. |
| `test/` | Ветка под эксперименты с тестами или CI. |
| `experimental/` | Прототипы и черновые ветки. |

После префикса допустимы только нижний регистр, цифры и дефисы. Имя ветки должно содержать смысловой идентификатор задачи или фичи.

## GIT-03. Защита веток

* Прямые коммиты в `main` и `develop` запрещены. Любое изменение проходит через PR.
* `force push` в `main` и `develop` запрещён без исключений.
* `force push` в общую feature-ветку, на которую опираются stacked-PR, запрещён без явного предупреждения участников цепочки.
* Слияние выполняется только после approve согласно `pullrequest.md`.

## GIT-04. Стратегия слияния

* Перед открытием PR ветка приводится в актуальное состояние относительно базовой ветки через `git rebase`, не через merge-коммит.
* Слияние релизного PR из `develop` в `main` — merge commit (`--no-ff`). Это сохраняет точку релиза.
* `git merge --no-ff` внутри feature-ветки не используется; для актуализации применяется только `git rebase`.

## GIT-05. Формат коммитов

* Формат сообщения: `[TASK-ID] <краткое описание>`.
* `TASK-ID` используется только в проектах, где ведётся трекинг задач по идентификатору. В остальных проектах префикс `[TASK-ID]` опускается, остаётся только описание.
* Краткое описание — до 72 символов, в повелительном наклонении, без точки в конце (пример: `[TASK-69] Add payment verification service`).
* Один коммит — одно логически связное изменение.
* Если изменение требует пояснений, после пустой строки добавляется тело коммита: что именно изменено, зачем.

## GIT-06. Релизы и тэги

* Релизные тэги ставятся на коммит в `main` сразу после слияния релизного PR.
* Формат тэга — `vX.Y.Z`, версия согласована с полем `version` в `vcpkg/vcpkg.json`.

## GIT-07. Запрещённые действия

* `git commit --no-verify` — pre-commit хуки обходить нельзя.
* `git push --force` в `main`, `develop` и в любые ветки, на которые ссылаются открытые PR.
* Коммит сгенерированных артефактов сборки (`build/`, `install/`, бинарники, кэши vcpkg).
* Коммит секретов, токенов и приватных ключей.
* Изменение чужого коммита (`git commit --amend`, rebase в чужой ветке) без согласования с автором.
